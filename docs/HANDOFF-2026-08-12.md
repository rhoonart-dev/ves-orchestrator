### Gemini 예비 키 (0025, 밤 추가)
**429 의 정체가 rate limit 이 아니었다.** 원문: `Your billing account has exceeded its monthly
spending cap`. 상한은 **키가 아니라 결제 계정**에 걸린다 — 같은 계정에서 새 키를 발급해도 똑같이 막힌다.
근본 해제는 `ai.studio/billing` 에서 상한을 올리는 것. 예비 키는 **다른 결제 계정** 것이어야 한다.

- `ves.env` 에 `GEMINI_API_KEY`(주) + `GEMINI_API_KEY_FALLBACK`(예비)을 함께 둔다. **6대 모두.**
- **어느 쪽을 쓸지만** DB(`ops_config.gemini_key`)가 정한다. 값이 아니라 선택이라 §5 불변식
  (시크릿은 env 파일에만)을 지킨다. 잡마다 읽으므로 **전환에 재시작이 필요 없다** — 6대가 다음 잡부터 함께 바뀐다.
- **자동 폴백**: 워커가 지출 상한 429 를 만나면 스스로 `fallback` 으로 넘기고, 쿼터로 한 시간 뒤에
  세워둔 잡들의 `run_after` 를 지금으로 당기고, Slack(`SLACK_WEBHOOK_URL`)으로 알린다.
  분당 rate limit 은 **넘기지 않는다**(기다리면 풀리는데 백업 계정을 태울 이유가 없다).
- **되돌리기는 사람이.** 관제 홈 배너의 `[주 키로 되돌리기]` 또는 `set_gemini_key('primary')`.
  자동 복귀는 플래핑을 만든다.
- 배선은 `executor._run_subprocess` 한 곳 — ai-video·brain 둘 다 `GEMINI_API_KEY` 만 알기에 엔진 무변경.
  ⚠ `localize` 는 여기 안 걸린다(자기 `.env` 의 `LLM_API_KEY` 를 쓴다).
- 관제 '맥·배포'에 맥마다 `🔑 예비 키 있음/없음` — 6대 배포가 어디까지 됐는지 보인다(heartbeat 보고).

## 5. 반복해서 당한 함정 (같은 실수 금지)

- **패치를 만들기 전에 반드시 `git fetch`.** 사용자가 이미 푸시한 것을 모르고 옛 base 로 패치를 만들어
  세 번 충돌시켰다. 항상 `git diff origin/main HEAD` 로 만들고, worktree 로 `git apply --check` 검증.
- **stop-hook 의 "미푸시 N건"은 내 클라우드 클론 기준이라 오보일 수 있다.**
  `git diff origin/main HEAD --stat` 이 비면 이미 올라간 것이다.
- **diff 패치를 채팅에 붙여넣게 하지 말 것.** 빈 줄이 "공백 한 칸"이라 복사 중 사라져 `corrupt patch` 가 난다.
  → `device_commit_files` 로 사용자 맥(`~/rhoonart/ves-fix.patch`)에 직접 써준다.
- **깃 푸시 ≠ 대시보드 배포.** S3 업로드를 따로 해야 한다(§7).
- **`ON CONFLICT DO NOTHING` 은 조용히 거짓 성공을 만든다.** 등록 수를 부풀리고 백필도 막았다.
  지금은 `DO UPDATE` + `RETURNING (xmax=0)` 로 신규/갱신을 구분한다.
- **`CREATE OR REPLACE VIEW` 는 컬럼을 끝에만 붙일 수 있다.** 중간 삽입은 이름 변경으로 취급돼 거부된다.
- **`_pick_source` 는 회차 번호가 '오래된 것 = 낮은 번호'라는 규약에 의존한다.** 등록 쪽을 고칠 때 함께 봐야 한다.
- **`priority` 는 큰 숫자가 먼저다** (`claim` 이 `ORDER BY priority DESC`, 기본 100).
  급한 잡에 50 을 줬다가 오히려 줄 맨 뒤에 세운 적이 있다. 앞세우려면 100 보다 크게.
  잡 하나를 지금 당장 앞세우려면: `UPDATE job_queue SET priority=200, run_after=now() WHERE id='…';`
- **이미 돌고 있는 프로세스는 나중에 넣은 `.env` 를 읽지 않는다.** 파이썬은 시작 시점에 읽는다.
  키·자산을 채운 뒤에는 **잡을 큐로 되돌려 새로 시작**시켜야 한다.
  워커 자체도 마찬가지 — `ves.env` 를 고쳤으면
  `launchctl kickstart -k gui/$(id -u)/com.rhoonart.ves-agent` (라벨은 하이픈이다. `deploy/launchd/` 확인).
  scheduler 노드(mm-01·mm-02)는 `com.rhoonart.ves-scheduler` 도 함께.
- **429 를 봤다고 rate limit 이라 단정하지 말 것.** 8/12 실측은 결제 계정 월 지출 상한이었고,
  이건 기다려도 안 풀리고 같은 계정의 새 키로도 안 풀린다. `error` 원문을 끝까지 읽어라:
  `select left(error,1400) from job_queue where id='…';` — 스택트레이스 뒤에 진짜 메시지가 있다.
- **quota 실패는 attempt 를 안 깎는다** — `dead` 가 되지 않고 한 시간마다 영원히 재시도한다.
  죽지 않아서 안심하기 쉬운데, 그동안 회전은 멈춰 있다. `error_class='quota' AND status='pending'`
  으로 따로 세야 보인다(관제 홈 배너가 이걸 띄운다).
- **`localize` 서브프로세스 타임아웃은 2시간**(`ves/adapters/localize.py`). `max_attempts` 는 3이라
  attempt 2 에서 타임아웃이 나면 곧장 `dead` 다. 오래 걸리는 실행은 attempt 를 미리 0 으로 되돌려 여유를 준다.
- **한 번 건넨 패치는 `--amend` 로 고치지 않는다.** 사용자가 그 패치를 적용하는 사이에 내용이 바뀌면
  같은 변경을 두 번 얹게 돼 충돌한다. 추가 변경은 **항상 새 커밋으로** 쌓고 새 패치를 만든다.
- **`CREATE OR REPLACE VIEW` 는 `WITH (security_invoker)` 를 안 쓰면 그 옵션을 날린다.**
  0022 가 그렇게 `source_usage` 의 invoker 를 떨어뜨려, 대시보드에 박힌 **공개 anon 키로 248행이
  그대로 읽히고 있었다**(실측: `set role anon; select count(*) from source_usage` → 248).
  0023 의 `source_usage_by_channel` 도 처음부터 없었다. 0024 가 `ALTER VIEW … SET` + anon REVOKE 로
  되돌렸다. **뷰를 새로 만들거나 갈아끼울 때마다 `security_invoker` 와 anon 권한을 같이 확인할 것.**
- **한 회차에 소스 파일 행이 여러 개일 수 있다.** 실측 8그룹(혜미리예채파 5화 3행 · 샤먼:미신전
  회차NULL 6행 · 피의 게임 X 4행 …). 소진은 (작품, 회차)로 세므로 **화면·수정은 회차 단위**여야 한다.
  파일 행 단위로 세면 '남은 편수'가 부풀고, 한 행만 고치면 사람이 기대한 대로 안 움직인다.
- **일이 한 맥에 몰리는 건 설계다** — §8 참고. "다들 노는데 하나만 밀린다"는 정상 동작일 수 있다.

## 6. 상태 확인 쿼리 (제어 DB)

```sql
-- 한눈에
select (select count(*) from review_queue where status='waiting') as 검수대기,
       (select count(*) from job_queue where status='running')     as 실행중,
       (select count(*) from job_queue where status='pending')     as 대기,
       (select count(*) from job_queue
         where status in ('failed','dead') and updated_at>now()-interval '24 hours') as 실패24h,
       (select left(last_seen_sha,7) from deployments where engine='orchestrator') as 배포sha;

-- 채널별 남은 회차 (0023 이후 정본)
select channel_slug, work_title, min(episode) as 다음회차, count(*) as 남은회차
  from source_usage_by_channel
 where remaining>0 and is_active and (duration_sec is null or duration_sec>180)
 group by 1,2 order by 4, 1;

-- 오늘 체인
select w.channel_slug, w.work_title, w.episode,
       string_agg(j.kind||'='||j.status,' ' order by j.created_at) as chain
  from work_orders w join job_queue j on j.work_order_id=w.id
 where w.created_at > now()-interval '20 hours' group by 1,2,3 order by 1;

-- 워커 상태
select node_id, status, disk_free_gb,
       round(extract(epoch from (now()-last_seen_at))) as 초전
  from node_registry order by node_id;
```

즉시 재계획: `INSERT INTO ops_config(key,value) VALUES('planner_kick', now()::text)
ON CONFLICT(key) DO UPDATE SET value=excluded.value, updated_at=now();`

그래서 **패치를 사용자 맥에 써주고 사용자가 올린다.**

```
cd ~/rhoonart/ves-orchestrator && git apply ~/rhoonart/ves-fix.patch \
  && git add -A && git commit -m "..." && git pull --rebase && git push
```

올라간 뒤 배포를 당기려면:
`UPDATE deployments SET last_seen_sha='<full sha>', updated_at=now() WHERE engine='orchestrator';`
(안 해도 version_watch 가 한 시간 안에 집는다)

## 8. 왜 일이 한 맥에만 쌓이나 (놀고 있는 맥이 도울 수 없는 이유)

맥 6대는 동질 워커처럼 보이지만, 잡은 **아무 데나 가지 못한다.** 두 겹의 제약이 있다.

**① 능력(capabilities)** — `node_registry.capabilities` 는 각 맥의 `VES_CAPABILITIES` 환경변수에서 온다.

| 능력 | 가진 맥 |
|---|---|
| generate · analyze · publish · network | 6대 전부 |
| **localize** | **mm-06 뿐** |
| scheduler | mm-01 · mm-02 |
| 인입(rclone.conf 보유) | mm-01 · mm-02 (`ops_config.drive_sync_nodes`) |

**② 노드 고정(어피니티)** — `generate` 가 만든 산출물은 **그 맥의 로컬 디스크**에 있다.
그래서 `executor._pin_dependents` 가 후속 잡(`upload_artifacts`·`ingest`·`evaluate`)에
`node:mm-0X` 캡을 박는다. 다른 맥이 가져가면 파일이 없어 즉사한다.

claim 은 `required_caps <@ effective_caps` 로 거른다. 그러니 `node:mm-06` 이 박힌 잡은
mm-06 이 바쁘든 말든 **mm-06 을 기다린다.** 다른 맥은 도울 방법이 없다.

여기에 `max_concurrency = 1`(6대 모두)이 겹친다. 한 맥은 한 번에 한 잡만 돈다.
그래서 mm-06 이 두 시간짜리 현지화를 잡고 있으면 그 뒤의 mm-06 몫이 전부 선다.

**mm-06 이 특히 몰리는 이유**: 한국 채널 5개(엔딩순삭·흥행수집·너굴안방·명장면세탁소·여운보관소)를
평소대로 돌리면서 **JP 현지화까지 혼자 맡는다.** 8/12 실측 24시간 처리량:
mm-02 43 · **mm-06 36** · mm-03 22 · mm-01 21 · mm-04 19 · mm-05 15.

### 손볼 수 있는 것
- **급한 잡을 앞세우기**(같은 맥 안에서의 순서만 바뀐다):
  `UPDATE job_queue SET priority=200, run_after=now() WHERE id='…';`
- **localize 를 두 번째 맥으로 넓히기** — 그 맥에 `video-localization-project` 자산(.env·가중치·venv)을
  갖추고 `VES_CAPABILITIES` 에 `localize` 를 추가한 뒤 워커 재시작. 지금은 mm-06 단일 장애점이다.
- **mm-06 의 한국 채널을 덜어 다른 맥으로** — 채널↔맥 배정을 옮기면 된다.
- ⚠ **어피니티 핀을 임의로 떼지 말 것.** 산출물이 그 맥에만 있어서 붙인 것이다.
  맥이 죽어 어쩔 수 없을 때만: `UPDATE job_queue SET required_caps=array_remove(required_caps,'node:mm-0X')
  WHERE work_order_id='…' AND status='pending';` (그 WO 는 generate 부터 다시 돌아야 한다)
